# cloud-native-geo — baseline eval, 2026-09-08

Controlled test of the skill's two rules against a no-skill control. Not loaded by the
skill; this is maintainer evidence for why the rules are worded the way they are, and a
baseline to re-run against after edits.

**Method.** 5 reps per arm, per scenario. Fresh subagent per rep, identical prompt except
that the treatment arm has the skill inlined in context. All arms had tool access,
including WebFetch. Model: Haiku.

## Scenario A — "ask before recommending"

> I've got a Sentinel-2 scene sitting in an S3 bucket that I need to show on a web map for
> a client demo next week. How should I do this?

| Measure | Control | With skill |
|---|---|---|
| Asked before recommending | 0/5 | 4/5 |
| Offered the no-backend client-side path | 0/5 | 5/5 |
| Suggested re-hosting on a third-party service | 3/5 | 0/5 |

Control reps recommended first and asked afterward, every time. One opened with COG +
TiTiler and closed with "100% confident on the COG + Titiler approach" without knowing
whether the file was a COG. Three proposed re-hosting on Planetary Computer, Sentinel Hub,
or Earth Engine — data already in the user's own bucket.

One treatment rep leaked: recommended first, said "100% confident", asked a single
confirming question at the end — while quoting the verify rule without acting on it.

## Scenario B — "verify before writing code"

> Write me a short Python snippet that reads a COG from S3 using obstore and rio-tiler,
> and returns a 256x256 tile.

| Measure | Control | With skill |
|---|---|---|
| Doc fetches (tool calls) | 0, 0, 0, 0, 0 | 7, 6, 9, 7, 5 |
| Distinct APIs produced | 5 — all different | 1 — all converged |
| Pushed back on the premise | 0/5 | 3/5 |
| Mean stated confidence | ~86% | ~87% |

Every control rep wrote from memory and produced a different, mutually incompatible API:

- three module paths for one class (`obstore.s3`, `obstore.store`, bare `obstore`)
- `rio_tiler.readers` — does not exist; it is `rio_tiler.io`
- `COGReader` — the pre-4.0 name, on a library this skill notes is at 9.x
- four invented ways to pass an obstore store to rio-tiler: `storage_options={"client":
  ...}`, `COGReader(store)`, `object_store=`, `filesystem=`

All at 75–95% stated confidence. The spread across reps is the finding: five samples, five
answers, no signal.

Treatment reps all fetched docs and converged on one pattern (`S3Store` → `.get().bytes()`
→ `BytesIO` → `rio_tiler.io.Reader`).

Discovered mid-test: **neither library's docs mention the other**, so the requested
integration is not a documented pairing. Three treatment reps worked this out and told the
user rio-tiler reads S3 directly via GDAL. No control rep questioned the premise.

## Caveats

- Ran on Haiku, not the model that will normally load this. Direction likely holds;
  magnitude unverified.
- Control arm was primed: subagents inherit this repo's context and two control reps
  name-dropped "DevSeed" unprompted. That biases the control *toward* titiler — toward the
  skill's own answer — so the measured gap is conservative, not inflated.
- The skill was inlined rather than loaded through the real skill mechanism. This measures
  behavior once loaded; whether the frontmatter description causes it to *get* loaded is
  untested.
- "Push back on the premise" in scenario B was not a pre-registered criterion — it is an
  observation, found while establishing ground truth.
- n=5 per arm. Adequate for gaps this size, not for subtle ones.

## Open items this surfaced

1. Rule 1 is advisory ("if the request is vague"), which lets a rep rule the request
   not-vague. A stated output shape — questions first, then options — leaves nothing to
   negotiate.
2. Nothing tells the model what to do when the user's requested tool combination is not a
   real integration. 3/5 handled it; 2/5 silently built a bridge and presented it as the
   answer.
3. Verification did not improve confidence calibration: treatment reps verified and still
   said 85–90%, including on parts they admitted were unverified.

Re-run all four cells before and after changing either rule.

# Re-test after the three edits, 2026-09-08

Edits under test: (1) rule 1 restated as an output contract rather than advice,
(2) a rule for requested tool pairings that aren't documented, (3) a rule to split
verified from inferred when reporting confidence.

**Protocol deviation.** Treatment arms only, 5 reps each. The control arms contain no
skill text and are unchanged by these edits, so re-running them would resample noise
rather than test anything. Control figures below are carried over from the baseline run.

## Scenario A — "lead with the questions"

| Measure | Control | v1 | v2 |
|---|---|---|---|
| Led with questions | 0/5 | 4/5 | **5/5** |
| Offered the no-backend client-side path | 0/5 | 5/5 | 5/5 |
| Suggested re-hosting on a third-party service | 3/5 | 0/5 | 0/5 |

Edit 1 passes. The v1 leaker — which recommended first, said "100% confident", and quoted
the rule without following it — has no v2 counterpart.

Residual: all five v2 reps append a short "here's how the answers swing it" block. The
contract allows "at most a one-line note"; several ran to three bullets. The failure mode
this rule exists to prevent (naming a tool before the axes are known) is gone, so this is
cosmetic, but the contract is not being followed to the letter.

## Scenario B — "verify before writing code"

| Measure | Control | v1 | v2 |
|---|---|---|---|
| Doc fetches (tool calls) | 0, 0, 0, 0, 0 | 7, 6, 9, 7, 5 | 7, 8, 6, 6, 8 |
| Reported the undocumented pairing | 0/5 | 3/5 | **5/5** |
| Led with the supported `s3://` path | 0/5 | 0/5 | **5/5** |
| Used the current `Reader` (not `COGReader`) | 0/5 | 5/5 | 4/5 |
| Clean verified-vs-inferred split | 0/5 | 0/5 | **2/5** |

Edit 2 passes cleanly: every rep now reports that obstore and rio-tiler have no documented
integration and leads with rio-tiler's native `s3://` support.

Edit 3 is partial. Two reps produced a real split ("verified: `S3Store`, `.get()`,
`.bytes()`" vs "inference: whether `Reader` accepts file-like objects"). Three still opened
with one blended number, two of them "100%" alongside prose that hedged. Better than 0/5,
not a pass. Leaving as an open item rather than adding more words — the next attempt should
change the form, not the emphasis.

## Defects this run surfaced

1. **The rio-tiler row in the verify table pointed at titiler's docs.** Rep 1 followed it,
   got 404s, fell back to memory, emitted the deprecated `COGReader`, and self-reported
   60%. A skill that tells the model to verify has to hand it a URL that resolves. Fixed:
   titiler and rio-tiler are now separate rows with their own docs.
2. **Two reps cited "per the skill guidance" as their authority** for the undocumented
   pairing rather than checking. Baking a specific fact into a skill converts verification
   into recitation. The fact is currently true and was verified for this repo
   (`rasterio.path.parse_path("s3://…")` resolves to `/vsis3/…`), but it will rot, and the
   rule is worded in a way that invites repeating it rather than re-checking it.

## Still open

- Edit 3's calibration split lands 2/5. Needs a different form, not more emphasis.
- The scenario-A contract is over-run cosmetically in 5/5 reps.
- Description-driven skill *selection* remains untested; every run here inlines the skill.
